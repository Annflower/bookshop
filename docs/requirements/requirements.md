# Требования (Requirements) — bookshop_py

> Документ описывает **текущее** состояние Python-проекта (`bookshop_py`) — FastAPI-бэкенда поверх существующей БД `bookshop_full`. Отражает фактические эндпоинты, роли и поведение (пройден по коду). Связанные документы: [user-stories](user-stories.md), [use-cases](use-cases.md), [bpmn](bpmn.md), [architecture](../architecture.md), [analytics](../analytics.md), [database](../database.md).

---

## 1. Назначение системы (Vision)

`bookshop_py` — это **FastAPI-бэкенд + одностраничный фронтенд** для книжного магазина, который переиспользует существующую БД `bookshop_full` (та же схема, что и в PHP-версии), НЕ пересоздавая её. Покупатель просматривает каталог, ищет книги (в т.ч. через ИИ-подсказки), добавляет в корзину, оформляет заказ, сохраняет книги в избранное и может оставить жалобу о проблеме с книгой. Владелец/администратор входит под аккаунтом с ролью `admin` и видит **дашборд аналитики** (KPI-карточки, заказы, продажи, выручка, города, отзывы, события, жалобы).

Параллельно система накапливает **факты заказов**, **события поведения**, **отзывы** и **жалобы** — пригодные для продуктовой, бизнес-аналитики и Data Science.

## 2. Заинтересованные стороны (Stakeholders)

| Сторона | Интерес |
|---------|---------|
| **Покупатель** | Найти и купить книгу, оформить заказ, сохранить в избранное, сообщить о проблеме. |
| **Владелец / Администратор** | Управлять магазином (роль `admin`), видеть аналитику и обрабатывать жалобы. |
| **Аналитик** | Получать чистые факты по заказам, выручке, городам, отзывам и событиям. |
| **Разработчик / DevOps** | Поддерживаемое окружение (venv, Docker), понятный API (Swagger), документация. |
| **Владелец бизнеса** | Выручка, средний чек, популярные товары, гео продаж, конверсии. |

## 3. Роли и доступ

| Роль | Как задаётся | Доступ |
|------|--------------|--------|
| `user` | по умолчанию при регистрации | каталог, корзина, избранное, жалобы, свои заказы |
| `admin` | вручную (`UPDATE users SET role='admin'`) | всё, что у `user` + аналитика и управление жалобами |

Вход единый (обычная кнопка «Войти»), отличие — в роли. Защита на бэкенде: `require_admin` (проверка `role == 'admin'`), иначе `403`.

## 4. Функциональные требования (FR)

### 4.1 Витрина / каталог
- **FR-1.** Покупатель видит список книг с ценой, автором и категорией.
- **FR-2.** Покупатель фильтрует каталог по категории (`?category=`).
- **FR-3.** Покупатель ищет книги по названию, автору, описанию (`?q=`).
- **FR-4.** Система показывает карточку товара (описание, наличие, цена, категория).
- **FR-5.** Для каждого товара фиксируется остаток (`in_stock`); при `0` покупка недоступна.

### 4.2 ИИ-поиск (смарт-матчинг)
- **FR-6.** Покупатель вводит фразу в ИИ-помощник; система нормализует её, раскрывает синонимы тем и возвращает релевантные книги с `score`.
- **FR-7.** Поиск работает без внешних моделей (idf-взвешивание + словари синонимов), limit 1–20 (по умолчанию 6).

### 4.3 Корзина (на стороне клиента)
- **FR-8.** Покупатель добавляет товар в корзину (клиентский `cart`), счётчик обновляется.
- **FR-9.** Покупатель меняет количество (`setQty`), удаляет позицию (`removeItem`).
- **FR-10.** Система показывает итоговую сумму и число позиций.

### 4.4 Оформление заказа
- **FR-11.** Покупатель вводит ФИО, email, телефон, адрес (и опционально `city`).
- **FR-12.** Система валидирует email и обязательные поля (Pydantic).
- **FR-13.** Заказ создаётся атомарно: покупатель (или гость по email) + заказ + состав + списание остатка + история статуса + событие в `event_log`.
- **FR-14.** Если пользователь авторизован — заказ привязывается к нему и профиль обновляется (`city` в т.ч.).
- **FR-15.** После создания заказ получает статус `new`; цена фиксируется в `order_items.price`.
- **FR-16.** API возвращает `{ order_id, total_amount, status }`.

### 4.5 Избранное (wishlist) — требует входа
- **FR-17.** Авторизованный пользователь добавляет книгу в избранное (`POST /favorites`) — идемпотентно, без дубликатов.
- **FR-18.** Пользователь видит список избранного (`GET /favorites`), удаляет (`DELETE /favorites/{id}`), проверяет (`GET /favorites/{id}`).
- **FR-19.** Счётчик избранного на фронте синхронизирован; сердечки в каталоге отражают состояние.

### 4.6 Жалобы / проблема с книгой
- **FR-20.** Покупатель (гость или авторизованный) сообщает о проблеме: книга, тип, описание, контакты (`POST /complaints`).
- **FR-21.** При создании жалобы пишется событие в `event_log`.
- **FR-22.** Администратор видит список жалоб (`GET /complaints`) и меняет статус (`PATCH /complaints/{id}`): `new`, `processing`, `resolved`, `rejected`.

### 4.7 Аналитика (только для `admin`)
- **FR-23.** Дашборд показывает KPI-карточки: заказы, выручка, клиенты, средний чек, города, отзывы, открытые жалобы.
- **FR-24.** Вкладки/витрины: `order-facts`, `product-sales`, `daily-revenue`, `event-log`, `cities`, `reviews`, `complaints`.
- **FR-25.** Аналитика по городам: число заказов, клиентов, выручка (группировка по `orders.city`, без отменённых).
- **FR-26.** Аналитика по отзывам: имя пользователя, название книги, оценка, текст, дата.

### 4.8 API и авторизация
- **FR-27.** Регистрация и вход возвращают подписанный токен и профиль пользователя.
- **FR-28.** Токен (Bearer) требуется для `/me`, избранного; аналитика и админ-жалобы — только `admin`.
- **FR-29.** Публичные эндпоинты: товары, категории, заказ, ИИ-поиск, создание жалобы, health.

## 5. Нефункциональные требования (NFR)

### 5.1 Производительность
- **NFR-1.** Каталог с поиском/фильтром — отклик в пределах разумного времени (пауза-лоадер на фронте ~250 мс для UX).
- **NFR-2.** Аналитические витрины на демо-объёме выполняются за время, пригодное для интерактивного дашборда.
- **NFR-3.** Индексы покрывают ключевые поля `JOIN`/фильтров (`category_id`, `user_id`, `order_id`, `product_id`, `email`, `created_at`, `city`).

### 5.2 Безопасность
- **NFR-4.** Все SQL-запросы — параметризованные (SQLAlchemy Core + `text`), без конкатенации строк.
- **NFR-5.** Пароли — PBKDF2-HMAC-SHA256 (`iter$salt$digest`), сравнение в постоянном времени (`hmac.compare_digest`).
- **NFR-6.** Токены — самоподписанные HMAC-SHA256 (`JWT_SECRET`), TTL 7 дней; секреты в `.env`.
- **NFR-7.** Аналитика и управление жалобами защищены проверкой `role == 'admin'` (`require_admin`), иначе `403`.
- **NFR-8.** Числовые значения корректно сериализуются (`Decimal` → `float`, даты → ISO).

### 5.3 Кодировка / интернационализация
- **NFR-9.** БД и соединения — `utf8mb4` (эмодзи, редкие символы).
- **NFR-10.** Интерфейс и ответы API — на русском языке.

### 5.4 Надёжность / целостность
- **NFR-11.** Создание заказа — атомарно (транзакция, откат при ошибке).
- **NFR-12.** Внешние ключи обеспечивают ссылочную целостность (в т.ч. `reviews`, `favorites`).
- **NFR-13.** Остаток не уходит в минус (проверка товаров при создании заказа).

### 5.5 Совместимость / окружение
- **NFR-14.** Python 3.12+ (проверено на 3.14.7), MySQL 5.5+, venv + `requirements.txt`.
- **NFR-15.** Docker: `Dockerfile` (Python 3.12-slim) и `docker-compose.yml` (app + MySQL 5.7).
- **NFR-16.** Перезапуск uvicorn после правок backend (без `--reload`).

### 5.6 Поддерживаемость / тестируемость
- **NFR-17.** Код разделён: `app/main.py` (маршруты), `services.py` (логика), `schemas.py` (валидация), `db.py` (доступ к БД), `auth.py` (пароли/токены).
- **NFR-18.** Swagger UI (`/docs`) доступен для проверки API.
- **NFR-19.** Документация покрывает требования, случаи, BPMN, архитектуру, схему, API.

### 5.7 Масштабируемость
- **NFR-20.** Аналитический слой (витрины `v_*`) отделён от операционного.
- **NFR-21.** При росте — можно вынести витрины/аналитику в отдельную OLAP-БД.
- **NFR-22.** Журнал событий растёт — предусмотрен лимит выборки (`limit`/`offset`).

## 6. Ограничения и допущения

- Оплата и доставка — вне зоны (заказ фиксируется, оплата не реализована, статусы модельные).
- Админ-панель как отдельный CRUD **товаров/категорий** на фронте не реализована — управление через существующую PHP-версию (`bookshop_full/admin/`); Python-проект даёт **аналитику** и **обработку жалоб** для `admin`.
- Роль `admin` задаётся напрямую в БД (нет UI-формы для смены ролей).

## 7. Критерии приёмки (Definition of Done)

- Покупатель может: каталог → поиск/ИИ → карточку → корзину → заказ; сохранить в избранное; подать жалобу.
- Владелец может: войти под `admin` → увидеть KPI и вкладки аналитики → обработать жалобу.
- Система пишет события, хранит историю статусов, отзывы, жалобы, избранное.
- API отвечает на базовые и защищённые эндпоинты; Swagger доступен.
- Все SQL-запросы параметризованы; пароли/токены соответствуют заявленным алгоритмам.
